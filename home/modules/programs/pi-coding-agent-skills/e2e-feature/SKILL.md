# End-to-end feature workflow

Use this workflow only when the user explicitly invokes `/skill:e2e-feature <request>`. Do not activate it for ordinary requests. This skill authorizes subagents only for independent review and verification; enable the `subagent` tool if it is not loaded yet. Design uses the separate visible Paseo tab below. `/skill:e2e-feature resume <handoff file>` continues a run that `e2e-dispatch` moved to this host: follow Resume after a host move instead of Preflight and Design.

You are the main agent and implementation owner, running on whatever model this session already uses; do not switch it. You coordinate design, implementation, review and E2E testing, and write the feature code, tests, harness changes and repairs yourself. In this skill, “orchestrator” and “parent” mean this same main session. Do not launch implementation, repair, setup or integration subagents. Reviewer and verifier children remain independent; design stays in its own visible Paseo tab.

If this skill was expanded by `/skill:e2e-feature`, its instructions are already in context; do not read this file again. Read linked references only when entering that phase.

This skill uses the Pi goal extension to execute the full approved plan. Every design requires final human review and explicit approval before handoff or implementation. The design agent must present the completed plan to the user, request final approval with `ask_user`, and wait for an explicit approving response before sending `PLAN_READY`. An approved plan means the exact plan the user reviewed and approved; answering design questions, invoking this skill, silence, and model self-approval do not satisfy this gate. Invoking this skill explicitly authorizes creating a session goal after the approved design handoff; do not run a second goal drafting or confirmation round. Keep human approval and design handoff before goal creation so automatic goal continuation cannot bypass the approval gate. One explicit approval of the completed plan satisfies this gate for both the design agent and orchestrator. Apply the approval delivery and reuse rules in Design brief and handoff; never ask again merely because the answer arrived asynchronously.

Stop and ask the user, with `ask_user`, only for: a destructive or irreversible operation, a security-sensitive action, a side effect outside the worktree other than the default-branch merge authorized below, a request so ambiguous that every path forward is a guess, or a gate this skill names. These are decision gates, not retry limits: ask only when the user must choose a requirement, scope, behavior, acceptance-criterion change, or authorization that the approved plan and existing instructions do not settle. Implementation defects, review findings, failing tests, and failed E2E steps are work to resolve autonomously, even after repeated failed attempts. Do not ask whether to keep fixing them or to accept broken behavior. Decide everything else yourself, record it as `Ruling: <decision> — <why> — <cost if wrong>`, and keep going.

## E2E requirement scope

Any isolated environment that can exercise the feature’s user journey end to end is acceptable. Isolation can come from a VM, a container, a disposable environment, or a local stack with separate test state; no particular isolation technology or terminology is required.

The agent must run end-to-end tests **only when a feature is first added**, subject to the repository's explicit “not needed” exemption below. Complete any necessary repairs and reruns during that initial feature workflow. Future pushes or deployments of the existing feature do not need to rerun those end-to-end tests. **Existing unit tests must still be run**, including for future pushes and deployments; skipping E2E tests does not waive unit testing.

Do not add E2E requirements for push or deploy to `AGENTS.md` (or `agent.md`). Any testing instructions requested or added by this workflow must state that the agent runs E2E tests when a feature is first added, future pushes and deployments do not require those E2E tests, and existing unit tests must still be run.

Whenever E2E actually runs, the repository root's `AGENTS.md` must contain named `qex-e2e` JSON resource declarations using the format in [references/qex-resources.md](references/qex-resources.md). Before first setting up a repository's E2E resource declaration or a new workload variant, obtain explicit human input through `ask_user` on the proposed CPU/RAM cost, covered stack and worker limits; follow the first-time setup gate in [references/qex-resources.md](references/qex-resources.md). Reuse an existing applicable declaration without asking on every run. Route every E2E stack, including smoke/capability experiments and reruns, through the independent verifier described below. This governs execution, not whether a new E2E run is required.

## Independent verifier

Only an independent verifier child loads and uses qex instructions in this workflow. Use the existing `worker` agent with the verification-only brief in [references/verifier.md](references/verifier.md); it reports evidence and owns no product/harness fixes. The exhaustive qex allowlist within that child is Gradle builds and complete E2E stacks; other verifier checks run directly. The main agent runs normal development checks directly under existing locks, without global qex instructions. Send verification selections containing an allowlisted command, including transitive prerequisites, to the verifier. Native `e2e-verify` and independent deterministic host gates remain available directly for selections whose entire dependency closure needs no qex. Never attach a qex-requiring gate to a reviewer or reserve a queued parent helper around queued leaves.

## Preflight

1. Pick a short, lowercase feature slug `<feature>`.
2. Confirm the current directory belongs to a Git repository and inspect the current Paseo workspace and Git worktree metadata.
3. If the current workspace is already a Paseo-owned Git worktree, use it and record its details as described in Feature worktree.
4. Otherwise, automatically create a new Paseo worktree workspace for the current project before doing feature work. Use the project's current branch as the base unless the user specified another base, and a feature branch named `feat/<feature>`. Discover the project ID from the current workspace or Paseo project registry; create the workspace with `paseo workspace create --isolation worktree --mode branch-off --new-branch feat/<feature> --base <base> --project <project-id> --title "<feature>" --json`. If the installed CLI uses different flags, inspect `paseo workspace create --help` and use the equivalent supported options. Verify the returned workspace ID, worktree path, owning project, base ref, branch, and `paseo/worktree.json`. Since the current agent cannot change its working directory, launch a fresh orchestrator agent in that workspace with the original user request and `/skill:e2e-feature` invocation, then end this turn. The new agent resumes at preflight using the created workspace; do not create a second worktree. If the CLI cannot create or associate the worktree, preserve the exact error and report the blocker; do not fall back to editing the current checkout or ask the user to create it manually.
5. For a request that adds a new feature, read the project-level `AGENTS.md` in `<worktree>` and classify its e2e status. For requests that do not add a new feature, skip this classification and the E2E phase; do not request or add E2E instructions:
   - **instructions**: it explains how to run an end-to-end test of a feature by walking through the user journey in an isolated environment, such as a VM, a container, a disposable environment, or a local stack with isolated state;
   - **not needed**: it explicitly says e2e testing is not needed for this repository;
   - **missing**: neither of the above, including when there is no `AGENTS.md`.
   When the status is missing, tell the user now, together with the design handoff below, so they can fix it while the design is underway. The gate is enforced in the e2e phase. When journey instructions exist, also read [references/qex-resources.md](references/qex-resources.md), inspect the actual stack/worker settings, and validate its root `AGENTS.md` declarations with `agent-job estimates --cwd <worktree>`. If an entrypoint needs its first resource declaration or a new workload variant, prepare a concrete CPU/RAM and worker-limit proposal from the actual stack and ask the user how to configure its qex cost using `ask_user`. Wait for their explicit choice before finalizing the declaration or running that workload, including a smoke/capability experiment. Record the choice alongside the declaration in this worktree's root `AGENTS.md`, include that file in task ownership, and validate the selected values. Reuse existing applicable declarations and recorded choices without duplicate questions; repair formatting without changing their resource policy. Assign any E2E smoke or representative capability experiment to the independent verifier after satisfying this gate and validating the declaration; the parent smoke check stays limited to direct non-qex checks. An explicit E2E exemption needs no resource declaration while no E2E is executed.
6. Run `e2e-feature-run init --feature <feature>` in the verified isolated worktree. This initializes runtime metadata and legacy ignore paths; goals use session-bound automatic continuation without project settings. Read [references/waiting.md](references/waiting.md) before goal creation.
7. Create the workflow mission described in Workflow layout and record its id. During design, perform the bounded host check below; before substantial implementation, prove the critical test path as described in Capability before implementation. Check destination capabilities before any host transfer.

## Feature worktree

Use an existing Paseo-owned Git worktree when the skill is invoked from one. When invoked from a local workspace or the main checkout, create a new Paseo-owned Git worktree automatically during preflight as specified above. Paseo places it under `~/.paseo/worktrees/<project hash>/<slug>` and records its base. All feature work, including the plan, implementation, commits, verification, and E2E runs, happens in that isolated worktree.

Verify and record it during preflight:

- `<worktree>` is `git rev-parse --show-toplevel` from your working directory. It is Paseo-owned when it lives under `~/.paseo/worktrees/` and `$(git rev-parse --git-dir)/paseo/worktree.json` exists.
- `<base>` is the `baseRef` field of that `worktree.json`, or `baseRefName` when `baseRef` is absent. This is the branch Paseo merges back into.
- `<workspace id>` is the entry in `paseo workspace ls --json` whose `cwd` is `<worktree>`.
- `<repo root>` is the main checkout: the first `worktree` entry of `git worktree list --porcelain`.
- The base commit is `git merge-base HEAD <base>`.
- `<branch>` is the current branch. Paseo may rename a placeholder branch after the first agent prompt, so read it again with `git branch --show-current` whenever you need it, not only once.
- `<git dir>` is `git rev-parse --absolute-git-dir`, this worktree's own Git directory, outside the tracked tree. Create `<run dir>` as `<git dir>/e2e-feature/<feature>` for briefs, findings, diffs, and E2E evidence. `<build lock>` defaults to `<git dir>/e2e-feature-build.lock`. Record command resource groups in `<run dir>/verification.md`: serialize commands sharing mutable build output, coverage destinations, generators, browser endpoints, or devices; allow concurrency only for proven independent groups. Use a common Git-directory lock when the resource is shared across worktrees. Unknown commands use the default lock. Record a small concurrency limit appropriate to the host; independent commands can still compete for CPU and RAM.
- Write `<run dir>/snap.sh`, which prints a tree id for the given paths (tracked and untracked, honoring `.gitignore`) without touching the index or the working tree:

  ```sh
  idx=$(mktemp -u) && GIT_INDEX_FILE=$idx git read-tree HEAD && GIT_INDEX_FILE=$idx git add -A -- "$@" && GIT_INDEX_FILE=$idx git write-tree; status=$?; rm -f "$idx"; exit $status
  ```
- Run `e2e-dispatch register --feature <feature>` from `<worktree>`. It records this run, your Paseo agent id, and your session in `<run dir>/run.json`, so `e2e-dispatch out` can move the run to another host overnight and `e2e-dispatch back` can bring it home. Skip this step when the command is not installed.

Never edit `<repo root>` during feature work; the final default-branch merge below is authorized. Set `cwd: "<worktree>"` on every `subagent` launch. Paths in this skill such as `docs/features/<feature>-plan.md` and `AGENTS.md` are relative to `<worktree>`.

Commit on `<branch>` only, after consolidated review acceptance unless isolation requires a recorded provisional checkpoint:

- the approved plan, as `<feature>: add plan`;
- each task once it is accepted, as `<feature>: <task id> <task title>`; combine ordered tasks sharing files into a coherent integration commit when necessary;
- each e2e repair, as `<feature>: fix <what>`.

Commit only the files the step changed. Keep generated artifacts and secrets out. Never commit to `<base>` directly.
## Workflow layout

Default to one coherent implementation task, T1, owned by the main session. Keep code, wiring and tests together. Split into sequential milestones only for a concrete dependency boundary, an external producer, or a useful checkpoint in a large change. Each additional task records `Split: <reason> — <why a separate milestone is needed>`. A task split never authorizes implementation subagents or concurrent writers. Use checkpoint files and compaction to manage context while preserving this role allocation.

Follow the approved dependency graph in the main session. Begin a dependent milestone once its prerequisite gates pass and its consumed interfaces match the plan. While an external producer is blocked, continue approved local work that does not depend on it. An external dependency handoff does not authorize spawning a producer worker under this skill. Preserve any explicitly planned early focused review; otherwise review the integrated feature after all implementation and gates finish.

Only reviewer and verifier children are launched, always as direct children without subdelegation. Verification uses the existing `worker` agent with a verification-only brief; its agent name does not authorize product, test or harness repairs. Keep relevant source, generated inputs and HEAD stable while children or host checks read them. Independent verification groups may overlap only with proven input/output and resource isolation. Commit at a safe point after affected readers finish.

Track implementation milestones in `<run dir>/tasks.md` and user-facing progress. Reserve subagent rows for review and verification:

- **Workflow row.** Create one mission before the first child launch with `subagent({ action: "mission.create", options: { mission: { title: "e2e-feature: <feature>", objective: "<one-line goal>" } } })`, and pass its `missionId` to every later review/verification launch.
- **Child rows.** Use one workflow script per launch, sent with `subagent({ workflow: true, async: true, cwd: "<worktree>", options: { missionId: "<mission id>" } })` in the same reply. Give each `runs.run(key, { label, phase, agent, task })` a stable lowercase key, a meaningful label, and phase `review`, `verification` or `e2e`. Save reports with explicit output paths and `outputMode: "file-only"`. Set `notifyOnComplete: true` for review/verifier boundaries; never launch an implementation child merely to populate a row.
- **Main-session progress.** Record each milestone as `pending`, `implementing`, `implemented (awaiting feature review)`, `fix rN`, `accepted` or `needs human`. Keep review scope and round counts separate.

Whenever you report progress, list completed milestones compactly and expand only active work. Include capability status, implementation/review state, required journey windows passed/discovered (plus failed, unrun and invalidated), remaining platforms/checks, current blocker with its age/dependency, and next action. Count coverage only on matching final inputs; a focused probe is not a full journey pass. Implementation acceptance never implies delivery.

```text
Workflow: e2e-feature: <feature>
├─ Design (separate Pi Opus / Pi Gemini tab)  ✓ plan approved
├─ T1 · main session                        ⟳ implementing
├─ Independent test gate                    · after stable implementation
├─ Review · complete feature                 · after test gate
└─ E2E · independent verifier                · pending
```

## Main-session context and child waits

Implementation and coordination share this session. Keep detailed logs on disk and preserve compact execution state so context growth does not create unnecessary handoffs:

- After launching async work, end your turn when nothing the plan requires is runnable. The runtime is expected to wake you when a run finishes, fails, or needs a supervisor decision, and to hold ordinary goal checkpoints while your runs are active; diagnose violations through `references/waiting.md`. Do not poll `status`, repeat progress reports, or fill the wait with work the plan does not need. A routine intermediate notice needs no action unless it is a designated task boundary. Review/verifier completion is a boundary: inspect the saved findings or receipts, then continue implementation, repair or acceptance in this session. Do not edit relevant inputs while a child or host check is reading them.
- Keep tool output small: tail or grep logs, read files by line range, cap command output, and never read binary files. Write briefs, findings, and diffs to files under `<run dir>` and give subagents the paths instead of pasting the content into your own context.
- Use the launch templates in this skill instead of looking up subagent syntax with `subagent({ action: "guide" })`. After required bookkeeping and async dispatch, yield when nothing is runnable; continuation is automatic and holds while this session has active subagent runs. When only a separate producer can make progress, declare its source-specific message wait as in `references/waiting.md`.
- Checkpoint the approved plan/approval reference, task state, unresolved findings and review counters, failed experiments and next hypothesis, protected boundaries, source/artifact identities, receipt paths and active child/job ids before a phase boundary. After design handoff, between stable milestones, or before a repair cycle, compact when useful using the supported session control; resume from those files and `get_goal`. Avoid unnecessary compaction in the middle of an unresolved debugging experiment; checkpoint its discriminating evidence first. Do not reread whole transcripts, recreate the goal, or spawn an implementation child merely because context grew.
- Return compact workflow receipts (`ok`, task, stage, `runId`, `outputReference`, and artifact paths). Save reports with `output` and `outputMode: "file-only"`; read findings by path when judging a review. Do not inline full reviewer or verifier reports into the main context. Persist the full approved goal objective; creation returns a compact id/status receipt without echoing the objective.
- An inactivity notice alone does not establish a stall. Inspect the named run once; preserve an active command or model request and wait for completion. Do not send routine continuation nudges, restart it, or launch replacement work while it is still active.
- Treat repeated checkpoints during a saved wait, missing completion wakes, duplicate continuations and blank resumed-verifier transcripts as runtime defects. Follow the diagnostic and regression contract in [references/waiting.md](references/waiting.md), using supported recovery and preserving live work. Skill prose does not implement a runtime fix; do not claim it does.

## Run state on disk

Keep the run's state in files as you go, not only in this session, so a new orchestrator can continue the run after a host move or a lost session:

- `<run dir>/tasks.md`: one line per task with its dependencies, state (`pending`, `implementing`, `implemented`, `fix rN`, `accepted`, or `needs human`), its implementation owner (`main session` and current session identity), checkpoint/changed paths, produced interface, gate receipt/input identity, and latest findings file. Record reviewer/verifier run ids separately for supported continuation. Keep consolidated scope coverage, review rounds, report paths, and acceptance in a separate `Review` entry. Update it whenever a task changes state.
- `<run dir>/status.md`: compact acceptance progress and time categories from [references/latency.md](references/latency.md), updated on meaningful state changes using existing events/receipts. Include exact blocked dependency, blocked-since time, next action/owner and supported wake/deadline. Surface a prolonged blockage through the existing attention/deadline mechanism or next native event; do not create polling turns or a watchdog daemon.
- `<run dir>/diagnosis.md`: current hypotheses, failed experiments and the next discriminating experiment when the reassessment triggers in [references/capability-and-repairs.md](references/capability-and-repairs.md) apply.
- `<run dir>/rulings.md`: append every `Ruling:` line.
- Each findings file also lists the findings you rejected, with your reasoning.
- `<run dir>/verification.md`: exact required check inventory, environment recipe, input identities, resource groups, test discovery, gate receipts, and evidence paths. Read [references/latency.md](references/latency.md) and [references/verification.md](references/verification.md) when preparing it. Use the latter's reusable JSON recipe and native `e2e-verify` workflow for deterministic checks. Record ready, launch, model/command start, lock acquired, finish, and acceptance times when available; distinguish external waits and human approval from execution. Use existing trace timestamps rather than spending model turns collecting timing data.

## Design

Read `$PASEO_AGENT_ID`; it is your own Paseo agent id, and the design tab uses it to hand the plan back to you. If it is empty, you are not running inside Paseo: drop the handoff paragraph from the brief and wait for the user to tell you the plan is ready instead.

Create a new, independent, user-facing Paseo agent for design, using Pi Opus (`pi/magpie/group/opus`) with thinking set to `high`. Both Pi Opus and the Pi Gemini fallback must use high reasoning. Do not use a Pi subagent, agent-scoped MCP creation, or a create-then-detach sequence for this phase. A plain agent-originated `paseo run` inherits parentage through `PASEO_AGENT_ID`; `--workspace` controls placement but does not remove parentage.

First capture the orchestrator's agent ID for the brief's explicit `PLAN_READY` handoff. The design agent goes in the same worktree workspace as you, `<workspace id>`. Then unset `PASEO_AGENT_ID` only for the design launch command with `env -u`, and pass the existing workspace explicitly. Keep the orchestrator's own environment and the daemon connection settings unchanged. This workflow explicitly authorizes creating the design session as a top-level agent:

```bash
env -u PASEO_AGENT_ID paseo run --no-wait --json \
  --provider pi/magpie/group/opus --thinking high \
  --workspace <workspace id> \
  --cwd <worktree> --title "Design: <feature>" \
  "$(cat <brief file>)"
```

Capture the returned agent ID and run `paseo inspect <design agent id> --json`. Require `ParentAgentId` to be `null`, and verify through Paseo's agent/workspace metadata that the agent belongs to the intended workspace. Then open it as a visible Design tab using `paseo agent open <design agent id> --json`, following Design brief and handoff below. If independence, placement, or opening fails, preserve the launch output and exact state and report the infrastructure blocker; do not silently proceed with a subagent or create duplicate design sessions.

### Pi Opus quota fallback

If Pi Opus is already known to be out of quota, launch Pi Gemini directly instead. If the Pi Opus design launch or a later design turn reports quota exhaustion or a usage limit that blocks design, replace that design tab with Pi Gemini automatically; do not wait for a quota reset or ask the user to approve the substitution. This exception applies only to Pi Opus quota exhaustion, not unrelated launch or infrastructure failures.

Before replacing an existing Pi Opus tab, preserve its agent ID, exact quota error, and any available design context. Prepare a replacement brief containing the original brief, the current plan file if present, and the design decisions, unresolved questions, and approval status available from the Pi Opus session. Archive the blocked Pi Opus agent with `paseo archive <old design agent id>` before launching the replacement, so only one design tab remains active. If Pi Opus never created an agent, skip the archive step.

Launch the replacement as an independent agent in the same workspace and worktree, keeping the original title and orchestrator's `PLAN_READY` handoff:

```bash
env -u PASEO_AGENT_ID paseo run --no-wait --json \
  --provider pi/magpie/group/gemini --thinking high \
  --workspace <workspace id> \
  --cwd <worktree> --title "Design: <feature>" \
  "$(cat <replacement brief file>)"
```

Apply the same independence and workspace checks to the replacement, and open it as a visible tab with `paseo agent open <replacement design agent id> --json` under the same mandatory opening and failure rules below. Then record its ID as the current design agent ID for all later messages and cleanup. Tell the user Pi Opus exhausted its quota and the design tab now uses Pi Gemini with high reasoning. Continue the existing design and approval process from the preserved context; replacing the tab does not approve the plan. If the fallback fails, preserve the exact error and report the blocker rather than repeatedly creating agents.

### Design brief and handoff

Every design session must open as a visible tab in Paseo Desktop, including a quota-fallback replacement. Creating an agent or finding it in the workspace's agent list does not satisfy this requirement. After verifying independence and workspace placement, run `paseo agent open <design agent id> --json` and require a successful open result before handing design to the user. Do not claim it is open or focused merely because creation succeeded. The open command requires a Desktop installation on the CLI machine; on a remote or headless host, or any open failure, preserve the existing design agent ID and exact error, report that opening the visible Design tab is blocked, and stop the handoff until opening succeeds. Do not substitute an instruction to find the agent in the agent list, create duplicate sessions, install Desktop, or change daemon configuration to satisfy this gate.

### Approval delivery and reuse

Treat an explicit user answer to the final plan approval request as valid whether `ask_user` returns it directly or the runtime delivers it later through a background notification or resumed turn. Match the answer to the pending question and reviewed plan revision using the available question/request identity and session context. The delivery channel does not invalidate the answer or require confirmation. A queued/pending receipt, silence, timeout, cancellation, tool-completion notice without a user answer, or an unrelated agent's assertion is not approval. While the request is pending, wait for its answer rather than opening a duplicate request. If an answer cannot be correlated, inspect the existing question/result or session evidence first; ask again only if the user's choice or reviewed revision remains genuinely unresolved.

Record the reviewed plan revision, approval question/reference, and explicit user answer once, then send `PLAN_READY`. Adding the Approval section or updating status metadata after approval does not change the approved design; retain the pre-approval revision identity and explain metadata-only differences instead of requiring a matching whole-file checksum. Both agents must reuse this record across handoff, continuation, quota fallback, and host moves. Renew approval only for a material change to the approved scope, behavior, acceptance criteria, design, or authorization, or genuinely missing/ambiguous approval evidence.

Write the brief to a temporary file first. It contains the user's request, what you learned in preflight, the approval delivery and reuse rules above, and these instructions:

> You are the design agent for this feature. You work in the feature worktree `<worktree>` on branch `<branch>`; do not edit anything outside it. Design the feature in this tab, exploring the code as needed. Ask for missing requirements when needed. Once the design is complete, save the plan and present its file link, a concise design summary, acceptance criteria, and material tradeoffs to the user. Use `ask_user` to request final human approval of this exact plan, offering approve or request changes, and wait for an explicit approving response. If changes are requested, revise the plan and request final approval again. Follow the supplied approval delivery and reuse rules: an explicit answer delivered through a background notification counts, and a pending request must not be duplicated. Record the approved plan revision, approval question/reference, and the user's approving response in an **Approval** section. Adding that record or updating status metadata does not itself require another approval. Do not send `PLAN_READY` before approval. Do not implement the feature or commit. The outcome of this session is one file, `<worktree>/docs/features/<feature>-plan.md`, which you keep up to date as the design evolves. It must contain these sections:
> - **Goal and acceptance criteria**: target behavior, then numbered criteria `AC1`, `AC2`, … that define feature readiness. Each criterion states one observable behavior or robustness property (correct results, error and failure handling, recovery, data integrity, concurrency, compatibility with existing callers), every user entry path or variant it must hold on (for example each editor, room vs thread, encrypted vs plain), and the exact evidence that proves it: a unit test, a check from Test and verification, or an E2E journey step. For a behavior criterion, the evidence must be an acceptance test that drives each named entry path through the real code implementing it (no fake or mock standing in for that code) and asserts the criterion's observable result; a unit test of a helper does not prove a user-visible criterion. List the state, lifecycle, resume, retry, and concurrency transitions the feature introduces (for example repeated or no-op calls, stale cached or copied state, restart and resume, failure then recovery, overlapping triggers) and give each one a criterion or a named regression test. Write verification criteria, such as baseline comparisons, in the exact wording acceptance will be judged by. Do not add criteria for code style, naming, formatting, or speculative hardening; repository lint and format checks cover style. Number required decisions `D1`, … and required documentation items so they can be traced the same way.
> - **Design**: implementation details, including module boundaries, data flow, interfaces with exact signatures, error handling, and the conventions to follow.
> - **Tasks**: default to a single task `T1` covering the whole feature, implemented by the main session. Split only into sequential milestones for a concrete dependency boundary, an external producer, or a useful checkpoint in a large change; each additional task records `Split: <reason> — <why a separate milestone is needed>`. Keep code, wiring and tests together. Give each task an id, goal, owned files, consumed/produced interfaces, dependencies and the unit test command proving it is done. Do not plan implementation subagents or concurrent writers. Account for active review/verification readers and shared generated inputs. A dependent milestone starts after prerequisite gates pass and interfaces match; it need not wait for unrelated external work or consolidated review. Explicitly identify any consequential interface or architectural uncertainty requiring an early focused review. Name external dependencies and local work that can proceed without them. Include checkpoints suitable for main-session compaction.
> - **Test and verification**: the complete unit, integration, lint, type, build, coverage, and visual check inventory required by the repository and request. Include exact commands, current runner and test-project discovery, environment prerequisites, generated inputs, concurrency conflicts, and which commands generate or rewrite files. Identify equivalent coverage/unit commands and reusable checks without reducing test scope. Include an isolated smoke check and cross-project dependency compatibility requirements. Include a consumer check: typecheck and build every package, app, or dependency-injection graph that consumes a changed interface, not only the changed package. Test contracts with code outside the feature against the real counterpart rather than hand-written fakes, unless the plan records why that is impossible. Name the host capabilities and one representative executable capability check for each materially different target: real entry, authoritative target readiness, representative action, actual observation method, required precision/cadence and evidence. Distinguish expected baseline feature failures from inability to observe the criterion. Sequence artifact production before consumers, and define coherent repair ownership and protected boundaries.
> - **E2E journey**: the user journey that proves the feature works end to end, written as steps with expected results.
>
> When the completed plan has received explicit final human approval, save the final file with its approval record and hand it to the orchestrator by running exactly this command; `--no-wait` matters, because the orchestrator's turn lasts the whole implementation:
>
> `paseo send <orchestrator agent id> --no-wait --prompt "PLAN_READY <worktree>/docs/features/<feature>-plan.md: approved by the user. <one-line summary and approval record reference>"`
>
> Never claim user approval unless the user actually gave it for the handed-off plan.

## Review

This fallback applies only to quota exhaustion, not other failures. The opt-in experiment in `references/reviewer-benchmark.md` is never an extra feature stage and never changes this setting automatically.

Default to one reviewer for the complete feature diff against the recorded base commit, including uncommitted and untracked additions. For a feature too large for one coherent review, use a few reviewers with explicit nonoverlapping responsibilities and one assigned owner for cross-module integration. Record the coverage map; do not recreate one review per implementation task or add a redundant full review on top of the partitioned reviews. Each review scope gets at most 3 rounds across the entire run, including later verification, E2E, and delivery repairs; a failed launch does not count. Do not reset the counter, rename a scope, or launch uncounted delta reviewers to bypass the cap. Generated, lint-only, formatting, and test-setup deltas with passing receipts and no product-behavior change can be verified by the orchestrator without another reviewer round: record a ruling. Write packets in normal prose. Require these review rules:

Report an untested transition as a finding with the regression test that would catch it.
   - **Readiness and robustness, not style.** Findings are defects that make the feature not ready or fragile in real use: wrong behavior, a missed path, broken wiring or interface compatibility, unhandled errors or failures, data loss or corruption, races, security issues, or regressions in existing behavior. When every fix in the round is local and its regression test meets that rule, verify it yourself from the test and host receipts and record a ruling instead of using a round. Launch focused verification reviews only for affected scopes whose fixes change state or lifecycle handling, contracts with code outside the diff, or security behavior. Check earlier findings as resolved or unresolved with evidence; request new findings only if Critical, or Important and introduced by the fixes.
