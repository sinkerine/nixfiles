# Execution placement and host moves

## Choose execution placement before moving

Before requesting or starting a transfer, compare the destination against the remaining verification work: available memory/disk and required peak headroom, native ABI/toolchain/device or emulator/KVM access, browser/display, reusable setup, isolated state/ports, artifact transfer cost and expected availability. Run the cheap host check against the actual destination, not the client machine. Save the result and unknowns in `verification.md` and pass them in the handoff. Recheck volatile capacity immediately before an expensive build; provisioned tools alone do not prove enough resources. Do not move to a host that can implement but cannot perform the known remaining critical test path without recording a concrete placement decision.

When supported by existing tools and authorization, prefer keeping the orchestrator/workspace in place and assigning an isolated remote test/build job to the capable host if this avoids a whole-workspace round trip. Such a job must use the exact source snapshot (including intended uncommitted changes), immutable artifact identities, separate state/resources and a durable evidence handoff. Remote diagnostic results do not replace the independent final journey/gates or authorize remote default-branch delivery. If the installed tools cannot provide that isolation/handoff, use the supported workspace transfer; do not invent a remote scheduler or transport. This is a placement option, not a new mandatory task split.

Use the installed dispatch/return skill for a transfer. Preserve its invoking-workspace exclusion: initiate the move from another workspace or terminal, never bypass it. Record the actual transfer owner, record id and completion event/deadline. A request or “started elsewhere” answer is not proof of destination readiness. Verify destination ownership, checkout/artifact identity and resumed tab before marking the move complete. Save a source-specific external wait where supported; surface transfer age and blocker in `status.md` instead of implying continuous execution or polling the source.

## Resume

`e2e-dispatch` moves a running run between hosts. It freezes the old orchestrator and its subagents, moves the branch, the uncommitted work, and `<run dir>` with paths rewritten for this host, and then starts you with `/skill:e2e-feature resume <handoff file>`. The old orchestrator and subagent runs have stopped; its goal is archived in the source host's session goal store. Their runtime ids do not work here.

1. **Orient.** Read the handoff file, a JSON record of the move: the feature, the two hosts, `home` (the host that delivers the run), the branch, the plan path, the accepted task commits, the subagent steps that were in flight, and the path of a copy of the old transcript. Redo the Feature worktree record for this worktree; it reuses the copied `<run dir>` and `snap.sh`, and its `e2e-dispatch register` step records you. Run `e2e-feature-run init --feature <feature>` to initialize runtime metadata before creating the new session goal; this never resumes a user pause. Do not create a worktree, a design tab, or a new plan.
2. **Rebuild the state** from `<run dir>/tasks.md`, `<run dir>/rulings.md`, the findings files, the `<feature>: <task id>` commits in `git log`, and `git status`; the uncommitted work moved with the run. Preserve the distinction between implemented and accepted tasks, plus consolidated review scope coverage and round counts. Restore `status.md` and `diagnosis.md`, capability evidence/limitations, exact blocked dependency and authorization boundaries; check the new host's remaining capabilities before restarting costly work. Do not infer acceptance from a provisional checkpoint commit. Revalidate moved gate input/environment identities before reusing evidence. Search the transcript copy only for details those files lack, and never read it whole.
3. **Restart tracking.** Create a new workflow mission, and a new execution goal as in Execution goal whose objective says it continues a moved run. If `previousGoals` in the handoff shows a paused goal, the user paused this run before the move: create the goal and immediately pause it in this user-triggered handoff turn with `update_goal({status: "paused"})`, then call `ask_user` to ask whether to continue before doing any work.
4. **Restart the steps that were in flight:** an implement step as a fresh worker told to continue from the task's current files, a review round from its start, and a fix round as a fresh worker given the same findings file and coherent repair-and-proof ownership. Preserve valid completed artifacts and revalidate host-dependent evidence instead of restarting setup blindly. Then continue the workflow from where it stands.
5. **Away from home.** E2E testing is allowed on both kazuki and sachi. Continue implementation, review, verification, and the required E2E journey on the current host when its test environment and dependencies are available; being on sachi is not a reason to defer E2E testing or request a return. If a required emulator, device, display, or other dependency is actually unavailable, report the concrete blocker and request a return only when the home host is needed to resolve it. On a host other than `home`, do not merge into the default branch, push, or archive the workspace unless the user explicitly invokes `/skill:merge-push-and-archive` or requests that delivery flow. That skill delivers completed work through the original Git remote, verifies the push, archives the workspace, and deletes its dedicated project registration only when no other active workspaces remain; kazuki can later pull the default branch without returning agents. Without that explicit delivery request, when only delivery remains, or a concrete test-environment blocker requires the home host, request the necessary return only if it is not already authorized and no supported isolated remote job resolves the blocker. Explain the exact resource/dependency and have the installed return skill initiate it from another workspace or terminal on either reachable host; never tell the invoking workspace to move itself. Reuse existing transfer authorization instead of asking again. If a human action remains necessary, use `ask_user` with that concrete action and the target host's reachability requirement. Otherwise record the existing transfer owner/event and wait through the supported mechanism, with blocked age and next action in `status.md`. Once back on `home`, deliver as usual.
