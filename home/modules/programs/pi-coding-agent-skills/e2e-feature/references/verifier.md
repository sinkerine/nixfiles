# Independent verifier child brief

Use this brief only for an independent verifier in `/skill:e2e-feature`. Launch the existing `worker` agent on `magpie/gpt-6.1-sol:medium` with this verification-only role; no new global agent or skill is required. Keep its run id for subsequent verification on stable inputs. An implementation or repair worker must not verify its own changes as this child.

The orchestrator writes `<run dir>/verifier-brief.md` containing this role contract and the exact assignment: absolute worktree, branch and source identity; approved plan and acceptance criteria; recipe path, selected check ids and their transitive prerequisites; existing build/device locks and resource groups; environment/artifact identities and pinned manifests; authorized setup/teardown and isolation boundaries; deadlines, evidence/report paths; and any retained owning host/qex job id. For a journey, also include the root `AGENTS.md` instructions, every expected journey step/window/variant, selected `qex-e2e` declaration, explicit CPU/RAM claims and exact command/worker limits. Resolve missing journey instructions through the main skill's human gate before execution.

Require the verifier to follow this contract:

- Read `~/.config/qex/AGENT.md` explicitly. These detailed qex instructions apply only to this verifier, never to the orchestrator or implementation/repair workers. Use qex only for Gradle builds (build, assemble, bundle and compile tasks, including wrappers) and complete E2E stacks, including capability probes and reruns. Run all other verifier checks directly under their existing locks. Ordinary development checks remain direct in implementation workers.
- Inspect recipe commands and wrappers, including every selected prerequisite. Put synchronous `agent-job run <profile> -- <command>` around each Gradle build leaf; choose an installed profile covering the entire workload and bound internal workers. For E2E, validate the root `AGENTS.md` declaration with `agent-job estimates --cwd <worktree>` and run the complete setup → test → teardown stack through `agent-job run --e2e <name> -- <command>` or managed `submit --e2e <name>`. Keep non-qex recipe commands direct. Record any run-local recipe adjustment and its identity; do not change product or harness code.
- Keep `e2e-feature-run verify` and the native `e2e-verify` helper outside qex. Invoke the selected helper checks from this child so their receipts, prerequisites and resource admission stay in one execution path. Never enqueue a parent helper as well as its leaves. An admitted E2E stack runs covered descendants directly after checking the owning job and declared resource scope; `AGENT_JOB_ACTIVE=1` alone is not a grant for another workload.
- Acquire existing build/device locks before qex admission. The recipe helper owns its legacy guard and declared resources; do not wrap it in an outer flock or reacquire its locks inside commands. For a standalone check use `flock --close <build lock> agent-job run <profile> -- <command>` (or `--e2e <name>`). Never wrap asynchronous submit in an external flock; use synchronous run or a qex-owned lock. Detached processes must not inherit an external lock or outlive their reservation.
- Reuse valid receipts on matching source, environment and artifact identities. Include root `AGENTS.md`, installed launcher/qex/profile identities, selected claims and command/worker settings in queued check evidence. Preserve isolation of filesystem, ports, display/device, state and generated inputs; qex admission does not provide isolation. Verify pinned manifests before and after journeys. Wait for overlapping writers/readers to settle or use authorized isolated inputs.
- Record owning host, retained job id, claims, command, source/environment identities, receipt and log paths, terminal exit status and per-step expected/actual results. A queued handle or child exit alone never proves success. Inspect receipts and actual evidence; report passed, failed, unrun and invalidated coverage explicitly.
- Keep the same qex job id after interruptions. The verifier already runs as an async background child: prefer one long bounded synchronous `agent-job run` or `qex status <job-id> --wait --timeout <duration> --json --no-logs` on the submitting host, with an explicit bash timeout covering queue wait plus execution and reporting margin. The parent stays responsive and native child completion wakes it. Use only the existing bash/host-command tool authority; do not request nested subagent tools or launch model children just to wait. Native `qex-wait` is optional only if this child runtime actually exposes the `subagent` tool, registered resource and authority for that exact native host wait (no model subdelegation); otherwise use the synchronous wait or an already supported detached host-command completion mechanism. No short status/sleep polling, duplicate submissions or nested reservations. Allow admission wait in the outer deadline. Missing qex, invalid declarations and rejected claims block execution; preserve the blocker without shrinking estimates, changing shared budgets or running the queued verification directly as a fallback.
- Do not edit product code, harnesses or regression tests, commit, or fix failures. On failure, reproduce once when safe, preserve evidence and report the hypothesis to the orchestrator for the implementation owner. Keep a failed environment only while its owning qex job remains active with the complete reservation; otherwise stop owned processes and obtain fresh admission before recreation. Tear down as authorized when finished. Diagnostic evidence never replaces the complete independent final journey on final inputs.

Launch with the assignment file, for example:

```js workflow
const verification = await runs.run("verify-t3-r1", {
  label: "Verify · T3", phase: "verification", agent: "worker", model: "magpie/gpt-6.1-sol:medium",
  task: "Act only as the independent verifier. Read <run dir>/verifier-brief.md and follow it exactly. Execute the assigned checks and report evidence; do not edit product or harness code or fix failures.",
  notifyOnComplete: true,
  output: "<run dir>/verify-t3-r1-result.md", outputMode: "file-only",
});
return { ok: verification.ok, verifierRunId: verification.runId, report: verification.outputReference, artifacts: verification.artifactPaths };
```

Do not attach a qex-requiring `gate` to an implementation run: that executes outside the verifier. The orchestrator may use native deterministic workflows or direct host gates only when the entire selected dependency closure contains no qex-requiring command. A mixed/full graph runs through the verifier; unrelated non-qex checks can still run directly with the same locks and receipts. After completion the orchestrator independently inspects saved receipts and evidence before releasing dependents or accepting work.
