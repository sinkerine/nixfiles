## Merge into the default branch

After all required work and checks pass, always commit the completed workflow-owned changes on `<branch>` and merge into the repository's default branch without another approval prompt. An explicit user instruction to keep the branch or open a PR instead overrides only the merge requirement; completed changes must still be committed. Do not mark the goal complete or send the final completion report until the commit and merge gates below pass. If blocked, preserve the worktree and report delivery as blocked, including the exact remaining step.

Use `<default branch>` as the target in every step below (even when the worktree's recorded `<base>` differs):

0. **Commit the verified work.** Inspect `git status --short`, the staged and unstaged diffs, and untracked files. Stage explicit workflow-owned paths and commit any remaining implementation, test, repair, plan, and required documentation changes on `<branch>`. Choose the commit message yourself. Exclude unrelated user changes, generated artifacts, and secrets. If hooks rewrite verified inputs, rerun the affected checks and verify the delta under the existing three-round code-review cap; once exhausted, use orchestrator inspection and independent host evidence as described in Review. Continue repairs autonomously until all required checks pass. Require a clean worktree and record the final feature commit; prior task commits satisfy this gate when no workflow-owned changes remain.

1. **Update from the default branch.** With a clean tree, run `git merge <default branch>` on `<branch>`. When the default branch tracks a remote, run `git fetch` first and merge the remote-tracking ref. Resolve conflicts in `<worktree>`: trivial ones yourself, substantive ones through a `worker`, and preserve the approved behavior autonomously. Ask the user only when resolving a conflict requires a genuine choice about requirements, scope, or behavior that the approved plan and existing instructions do not settle. If the merge brought in changes, rerun the plan's Test and verification checks. Rerun the e2e journey only when this run adds a new feature and the E2E phase is required; merging, pushing, or deploying alone does not introduce an E2E requirement.
2. **Find the target checkout.** Find the worktree that has `<default branch>` checked out with `git worktree list --porcelain`; usually that is `<repo root>`. Merge only if `git -C <target> status --porcelain` is empty. Otherwise ask the user; never stash, reset, or discard work in their checkout. If `<default branch>` is not checked out anywhere, merge in `<worktree>` itself: check out `<default branch>`, merge, then check out `<branch>` again, as Paseo does.
3. **Merge to the default branch.** Run `git -C <target> merge <branch>`. Squash only when `AGENTS.md` or the user asks for it: `git -C <target> merge --squash <branch>`, then `git -C <target> commit -m "Squash merge <branch> into <default branch>"`. If the merge conflicts, run `git -C <target> merge --abort` and go back to step 1.
4. **Confirm before completion.** For a normal merge, require `git -C <target> merge-base --is-ancestor <branch> <default branch>` to succeed. For a requested squash merge, verify the squash commit contains the intended feature changes. Confirm the target checkout is clean, record `git -C <target> rev-parse <default branch>`, and include the feature commit, target branch, resulting commit, and verification evidence in the final report. Any changed integration inputs must have passing checks as required in step 1. Only then mark delivery and the goal complete. Push only when the user asked for it.
## Clean up the worktree

In Paseo, cleanup means archiving the workspace. Archiving runs the teardown commands from the project's `paseo.json`, force-removes the Paseo-owned worktree with `git worktree remove --force`, prunes it, and archives every agent and terminal in the workspace. It keeps the branch.

Because the removal is forced, archive only after the branch is merged, or after the user explicitly says to discard it, and only once `git status` is clean, so nothing uncommitted is lost. If the user chose to keep the branch, leave the workspace in place and say so.

1. Confirm every worker and the design tab are archived, and tear down any test environment the e2e instructions started.
2. You run inside this workspace, so archiving it stops you too. Deliver your final report first. Then tell the user to archive the workspace from Paseo, from the workspace's Archive action in the sidebar. If they ask you to do it, run `paseo workspace archive <workspace id>` as your very last command.
3. Paseo leaves `<branch>` in place. Delete it only when the user asks: `git -C <repo root> branch -d <branch>`, which refuses unmerged work.

For a subagent or Paseo infrastructure failure, preserve the exact error and the Git and worktree state, and use the tool's supported recovery path before retrying. Beyond the pi-subagents workflow scripts described here, do not build custom scripts, schedulers, daemons, or automatic production changes. This workflow handles one feature at a time and stops when recovery makes no progress.
