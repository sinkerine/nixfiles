
## Independent E2E verifier queue reference

This reference is not appended to common agent instructions. Its queue policy applies only to the independent verifier child in `/skill:e2e-feature`, whose verification-only brief loads `~/.config/qex/AGENT.md`. The executor runs normal development checks directly under existing locks, the verifier runs independent checks, and the orchestrator coordinates and inspects evidence.

All projects and workspaces on this host share the Nix-managed `qex` coordinator. Required qex admission uses an exhaustive allowlist: **Gradle builds and E2E tests only**. Gradle builds include `gradle`/`./gradlew` build, assemble, bundle and compile tasks, including wrappers that invoke them. E2E includes browser/Electron/native tests and their complete setup/teardown stacks. All other commands run directly, including Nix builds/checks, other builds, unit tests, lint/format, typechecks, coverage, dependency installation and standalone VM work, unless they are part of an admitted E2E stack. Before an allowlisted operation, read `~/.config/qex/AGENT.md`. Submit Gradle builds with `agent-job submit <profile> -- <command> [args...]` (or synchronous `agent-job run`); `agent-job profiles` lists the authoritative estimates: `small` (1 CPU, 2 GiB), `medium` (2 CPU, 4 GiB), and `heavy` (4 CPU, 8 GiB). Choose from the complete workload and worker count, not currently free RAM; never downsize a claim to fit. If none fits, report the required resources. E2E uses the repository declaration below. qex configuration and profiles are managed in Nixfiles through `my.programs.qex`; edit and activate the Nix configuration instead of using `qex config set` or editing installed files.

**Every E2E execution requires qex admission before starting the test stack**, including smoke tests, capability probes, manual journeys, retries, and independent verification. Read the matching named `qex-e2e` JSON block in the repository root's `AGENTS.md`, validate it with `agent-job estimates`, and run `agent-job submit --e2e <name> -- <command> ...` (or `agent-job run --e2e <name> -- <command> ...` for a managed synchronous check). The declaration uses qex job-file fields `resources.cpu` and `resources.mem` with explicit values; read `~/.config/qex/AGENT.md` for the format. Missing or invalid declarations, unavailable qex, or rejected claims block E2E execution; do not fall back to an unqueued command, a global profile, or a file lock alone. Submission is a request: qex must start the resource-consuming command before it has quota. Keep that reservation for setup, execution and teardown. Descendants can run directly only within an already admitted E2E workload whose recorded claim covers them; `AGENT_JOB_ACTIVE=1` alone is not a new quota. This rule governs how E2E runs, not when a repository must require E2E.

Use the returned job ID for status, logs and cancellation; never resubmit just because a job is queued or a wait was interrupted. Use the harness's background completion mechanism for long waits. The async background verifier can use one long bounded synchronous `agent-job run` or `qex status --wait` with an explicit tool timeout covering queue wait plus execution. Its parent remains responsive and child completion wakes it. Use native `qex-wait` only when that runtime already exposes its tool/resource and exact native host-wait authority; never require model subdelegation or extra nested tool privileges to wait. The CLI alone does not wake a session. Never repeat short status/sleep polls; without a background mechanism, inspect once and report the retained job ID. Commands inside an existing queued job run directly: never queue both a parent runner and its children. Keep the entire resource-consuming stack alive under its job through teardown. Preserve existing build/device locks and verification receipts. Work guarded by an external lock must use synchronous `agent-job run` under that lock, or use a qex `--lock` held with the job; never wrap asynchronous `agent-job submit` in `flock`, because the lock is released on submission. Read global queue status before rerunning checks; a queued launch is not a passing result. Do not change shared host budgets without explicit user authorization, create project-specific queue state, enable qex memory learning, or cancel another workspace's job to get your command started. Qex admission is based on estimates and does not impose hard CPU/RAM limits.
