
## Shared build and test queue

All projects and workspaces on this host share the Nix-managed `qex` coordinator. Before builds, tests, coverage, browser/Electron E2E, native builds, or VM jobs, read `~/.config/qex/AGENT.md`. Submit expensive commands with `agent-job submit <profile> -- <command> [args...]`; `agent-job profiles` lists the authoritative estimates. For non-E2E work, use `small` for focused unit/lint checks, `medium` for typecheck or modest builds, `native` for native builds, and `heavy` for unfamiliar expensive commands. E2E uses the repository declaration below. Choose from workload and worker count, not currently free RAM; never downsize a claim to fit. Reads, searches, Git inspection, and trivial scripts can run directly.

**Every E2E execution requires qex admission before starting the test stack**, including smoke tests, capability probes, manual journeys, retries, and independent verification. Read the matching named `qex-e2e` JSON block in the repository root's `AGENTS.md`, validate it with `agent-job estimates`, and run `agent-job submit --e2e <name> -- <command> ...` (or `agent-job run --e2e <name> -- <command> ...` for a managed synchronous check). The declaration uses qex job-file fields `resources.cpu` and `resources.mem` with explicit values; read `~/.config/qex/AGENT.md` for the format. Missing or invalid declarations, unavailable qex, or rejected claims block E2E execution; do not fall back to an unqueued command, a global profile, or a file lock alone. Submission is a request: qex must start the resource-consuming command before it has quota. Keep that reservation for setup, execution and teardown. Descendants can run directly only within an already admitted E2E workload whose recorded claim covers them; `AGENT_JOB_ACTIVE=1` alone is not a new quota. This rule governs how E2E runs, not when a repository must require E2E.

Use the returned job ID for status, logs and cancellation; never resubmit just because a job is queued or a wait was interrupted. Use the harness's background completion mechanism for long waits. The CLI alone does not automatically wake a Pi/Paseo session. Commands inside an existing queued job run directly: never queue both a parent runner and its children. Keep the entire resource-consuming stack alive under its job through teardown. Preserve existing build/device locks and verification receipts. Work guarded by an external lock must use synchronous `agent-job run` under that lock, or use a qex `--lock` held with the job; never wrap asynchronous `agent-job submit` in `flock`, because the lock is released on submission. Read global queue status before rerunning checks; a queued launch is not a passing result. Do not change shared host budgets without explicit user authorization, create project-specific queue state, enable qex memory learning, or cancel another workspace's job to get your command started. Qex admission is based on estimates and does not impose hard CPU/RAM limits.
